# 26 对话执行轨迹

## 1. 定位

对话执行轨迹是面向终端用户的 Session 查询投影。它解释一次对话如何经过模型、Capability、
MCP、Tool、Skill、Resource 与人工审批得到结果，但不承担任务事实写入、结果交付或运维排障。

它与另外三条读取路径严格分离：

- transcript 只恢复用户与助手消息以及当前待审批卡片；
- activity 恢复产品级执行轨迹；
- result 返回权威 Run 结果；
- operations timeline 混合 Canonical Event、trace、audit 与 alert，仅供运维排障。

Canonical Session Events 仍是唯一事实源。Activity 可以删除并从事件重建；SSE 只通知 UI 增量
刷新，不能成为历史事实源。

## 2. 公开契约

```text
GET /v1/tasks/{session_id}/activity?after_version=0&limit=200
```

响应包含 Task `projection_version`、本次读取到的 `source_version`、稳定 Activity nodes、
`next_after_version` 与 `has_more`。`after_version` 使用 Session aggregate version，不暴露 Kafka
offset。增量响应可能再次返回同一个 node；消费者必须按 `id` 以较大的 `updated_version` 覆盖，
从而把 requested/completed 等生命周期折叠成单节点。

每个节点至少包含：

- `id`、`type`、`status`、`title` 与安全摘要；
- 首次出现的 `sequence` 与最后变化的 `updated_version`；
- `run_id`、开始/结束时间、可计算时的 `duration_ms`；
- 关联 ID（event、model call、tool invocation、skill activation、approval）；
- 有界、递归脱敏的 `detail`。

## 3. 节点与折叠

| Activity 类型 | Canonical Events | 折叠键 |
|---|---|---|
| `user_prompt` | `session.created`, `user.message.appended` | event ID |
| `model_input` | `model.input.prepared` | run + model call ID |
| `model_output` | `model.turn.completed`, `model.output.completed` | run + model call ID |
| `tool` | `tool.call.requested/completed/denied` | run + tool invocation ID |
| `skill` | `skill.activated/completed/failed/cancelled` | run + skill activation ID |
| `resource` | `context.resource.used` | event ID |
| `approval` | `approval.requested/approved/rejected/expired/cancelled` | run + approval ID |
| `run` | `run.requested/scheduled/started/retry_scheduled/completed/failed/cancelled/terminated` | run ID |
| `session` | `session.paused/resumed/closed`, `runtime.failed/reprovisioned` | event ID |

不同 Run 的相同 invocation/activation ID 不得合并。节点初始顺序使用首次 aggregate version；
增量游标使用 `updated_version`，避免生命周期终态丢失。

## 4. 模型输入证据

Runtime 在每次模型调用前追加 `model.input.prepared`，只保存可公开证据：

- model call ID、turn index、消息/角色计数；
- 最后一个用户消息的有界预览；
- 输入与 Tool schema 的 SHA-256 digest；
- 已暴露的 Tool 名称、首选模型、允许 provider、数据分类和输出预算。

事件不得保存完整 system prompt、Skill 正文、Resource 正文、隐藏指令或 Chain-of-Thought。
Digest 用于关联与审计，不用于恢复模型请求正文。

## 5. Capability 与 MCP 来源

`tool.call.requested` 附带独立的 `activity` 来源元数据。内置控制能力标记为 `auraclaw`；从
Capability Catalog 加载的 Tool 带 `capability_id`、`kind`、`server_id` 和 `source=mcp`。
UI 不根据 Tool 名称前缀猜测 MCP 来源。

## 6. 安全与容量

- API 在租户范围确认 Task 存在，跨租户保持 404 语义。
- 参数和结果先按敏感 key、Bearer 与 Private Key 规则脱敏，再进行大小限制。
- 超过限制的 detail 返回 digest、有界 preview 和 `truncated=true`，不返回任意大对象。
- 模型最终文本只在 transcript/result 完整展示；Activity 默认使用摘要与 usage。
- Activity 响应使用私有缓存语义；应用本地只缓存面板展开偏好和查询缓存，不持久化详情。

## 7. AuraX 消费规则

- 初次打开读取完整页，后续用 `after_version` 拉增量，并按 node ID/updated version 合并。
- SSE 收到任意 Session 可见事件时仅使 activity query 失效。
- 按 Run 分组后使用 `sequence` 排序；无 Run 的 Session 节点进入“会话”组。
- 右侧面板可折叠；窄窗口切换为覆盖式抽屉，不能缩窄聊天正文至不可用。
- loading、empty、error、retry、running、waiting、failed 与 cancelled 均有独立可访问状态。

## 8. 当前实现摘要

- 归属：`gateways/query/activity.py`、`gateways/query/transcript.py`、`api/routes/tasks.py` 与
  Runtime `model.input.prepared`/tool/skill/resource/approval/run Canonical Events。
- Activity 已实现节点折叠、增量 `after_version`、有界递归脱敏、来源元数据和 duration/status 计算；
  Transcript 单独恢复消息与待审批卡片。
- 该能力作为 `task-api` 查询逻辑部署，不新增事实库或第 13 个生产进程。

## 9. 现有缺陷与待完善

- Activity 当前按请求读取 Canonical Events 并构建，超长对话的性能、预计算投影和缓存策略尚未形成基线。
- 模型输入只保留 digest/有界证据，无法用于逐字复现 provider request；需要受控 Debug Artifact 才能扩展取证。
- Tool/Skill 的摘要依赖事件生产者提供稳定元数据，旧事件和未知新事件的展示可能退化为通用节点。
- AuraX 消费规则是跨仓库契约，本仓库没有前端可访问性、布局和合并逻辑的端到端证明。
- 待补：activity schema version、旧事件兼容 fixtures、大 Session 压测、跨仓库契约测试和导出/审计策略。

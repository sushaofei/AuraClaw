# 循环和控制
## 解决的问题
一次性问答 → 循环系统
- 执行周期：**接收状态 → 检索上下文 → 规划 → 行动 → 观察 → 更新计划/继续执行**
- 终止条件：**最大步数**、**递归深度**、**单步成本上限**和**超时约束**等
## 内涵
**约束**智能体的**时间结构**和**执行路径**。
表达力 vs. 可终止性
## 设计原则
- 循环必须有明确的**终止条件**
- **规划**与**执行**应尽量分离
- 递归和子任务生成必须有**预算**
- 失败不是异常，而是循环状态的一部分
## 实现方案
### 单循环 ReAct 架构
```
while not done:
	observe state
	model decides next action
	execute action
	append observation
```
**优点**
- 实现简单
- 灵活
- 适合探索性任务
**缺点**
- 难控制
- 容易冗长
- 对复杂任务规划能力不足
**关键控制点**
- 设置硬性护栏：`max_steps`、`timeout`、`budget`
- 限制重试与回退次数，避免同类错误无限循环
- 对工具调用增加白名单与参数校验
**适用场景**
- 开放式探索、原型验证、低风险自动化
**常见失败模式**
- 反复试错但无进展（looping）
- 局部最优动作导致整体任务漂移
### 规划-执行架构
```
plan = planner(goal)
for step in plan:
	result = executor(step)
	if failed:
		plan = replanner(goal, history)
```
**优点**
- 可解释性好
- 容易插入审批点
- 容易估算成本
**缺点**
- 初始计划可能过早固化
- 对动态环境适应性稍弱
**关键控制点**
- 计划要版本化（`plan_v1`, `plan_v2`），保留变更原因
- 为重规划设置触发条件：失败阈值、外部状态变化、成本超限
- 把“规划模型”和“执行模型”分开，减少串扰
**适用场景**
- 有明确目标与步骤的任务（发布流程、数据处理流水线）
**常见失败模式**
- 计划过细导致执行僵化
- 频繁重规划导致吞吐下降
### 分层多智能体架构
```
Supervisor Agent
	├── Coding Agent
	├── Search Agent
	├── Data Agent
	└── Review Agent
```
**优点**
- 适合复杂任务
- 权限可以按智能体分层
- 工具集可以专业化
**缺点**
- 编排复杂
- 通信开销高
- 容易出现责任边界模糊
**关键控制点**
- 明确每个 Agent 的输入/输出契约与责任边界
- 统一任务分发协议（优先级、超时、重试、回执）
- 由 Supervisor 管理全局预算与冲突仲裁
**适用场景**
- 跨领域、长链路、需要并行协作的复杂任务
**常见失败模式**
- 子 Agent 目标不一致导致“各做各的”
- 上下文传递失真造成重复劳动
### 状态机/工作流图架构
```
Node: Plan
Node: Retrieve
Node: Execute
Node: Verify
Node: HumanReview
Node: Finish
```
**优点**
- 可控性强
- 适合生产系统
- 易观测、易测试
**缺点**
- 灵活性低于自由智能体
- 需要提前设计状态和转换条件（转移边）
**关键控制点**
- 每个状态定义清晰的进入条件、退出条件和失败处理
- 将人工审批节点显式化（HumanReview）
- 对关键状态埋点，支持追踪成功率与耗时
**适用场景**
- 高合规、高可靠、可审计要求强的生产任务
**常见失败模式**
- 状态爆炸导致维护成本飙升
- 图设计不完整引发死锁或无效分支

## 选型建议（工程视角）
- 如果优先追求**上线速度与灵活探索**：先用单循环 ReAct，但必须加硬护栏。
- 如果优先追求**可解释和成本可预测**：优先规划-执行架构。
- 如果任务天然跨角色且并行性高：采用分层多智能体，但先定义契约再扩容。
- 如果优先追求**稳定性、可审计与可测试**：优先状态机/工作流图架构。

## 最小控制基线（建议所有方案统一具备）
- 统一终止条件：步数、超时、预算三重上限
- 统一失败语义：失败可恢复、可重试、可降级、可上报
- 统一观测指标：成功率、平均步数、重试率、单任务成本
- 统一人工接管：达到阈值后自动切换 HumanReview
